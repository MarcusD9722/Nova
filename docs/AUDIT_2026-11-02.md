# Full audit: memory/ core/ backend/ plugins/

**Date:** 2026-11-02. **Head:** `473cc49`. **Mode:** find and report. No repo code
was changed by this audit.

> **C1, the security hole described below, is fixed.** This report was written
> while it was open, and it was committed only after the fix (`a9ffa32`). All 59
> findings have since been fixed. `docs/AUDIT_2026-11-02_FIXES.md` records how,
> and what proved each one.

The request was to read how the four packages work and connect, check that the
code does what it is meant to, hunt for silent failures, and then run Nova for
real, in conversation and on a coding exercise, to see whether she can think,
plan, implement and execute.

## Bottom line

**The foundations are strong. The layers in front of the model and around its
output are not.**

The storage layer, the goal and task state machine, the permission broker, the
TTS isolation and the speaker scoping are careful, and they held up under
everything thrown at them. With real weights Nova holds a warm conversation,
remembers across sessions, reasons acceptably and writes real code that mostly
works.

The serious problems cluster in four places:

1. **One security hole needs closing now.** `/dev/propose` plus `/dev/apply` runs
   arbitrary code with no authentication, and the real `.env` has `NOVA_DEV_MODE=1`
   and no API token.
2. **Stopping a reply kills the process.** Timeouts and early exits release the
   GPU permit while the worker thread is still inside llama.cpp. Closing a reply
   mid-stream, which the Stop button, a new message and voice barge-in all do, was
   fatal 7 times out of 7 on the first try. There is no error, just exit 127.
3. **Regexes in front of the model decide too much.** Ordinary sentences never
   reach her. "My marriage isn't working." starts a project improvement. "Find
   the bug:" gets a Google Maps error.
4. **She cannot tell what actually happened.** She says work happened when it did
   not, "I've wiped that locker code" after the tool failed, and "Logic tests
   passed" when zero tests ran. Three builds exercised three different holes in
   verification, and none reached `complete`.

All 186 test suites pass, and that is not in tension with the above. The harness
replaces the model with `ScriptedLLM`, so 34 of the 36 functions in
`core/llm_runtime.py` have never run under test, and reply quality has never been
tested at all. C2, C4 and much of the High tier sit in that gap.

## Do these today

These need no code change.

1. **Turn developer mode off when you are not using it.** Set `NOVA_DEV_MODE=0` in
   `.env`. This closes the code execution route (C1).
2. **Set an API token, but not in `.env`.** Electron does not read `.env`, so a
   token set only there makes the backend demand something the UI does not have,
   and everything returns 401. Set `NOVA_API_TOKEN` as a Windows user environment
   variable, or add a `$env:NOVA_API_TOKEN = "..."` line to `start_nova.ps1`, so the
   backend and Electron both inherit it. This corrects the advice given after
   cleanup E, which said to put it in `.env`.
3. **Let replies finish.** Until C2 is fixed, do not press Stop or send a new message
   while she is still generating. If Nova ever dies with no error, this is the likely
   cause.
4. **If she suddenly gets very slow, restart her.** One image keeps a second copy of
   the model in VRAM until restart (H21).

## What works, and works well

Not everything here is a problem, and these deserve saying plainly.

- **Goal and task state machine.** Generation fencing, atomic decision application
  and the separation of status from outcome are better than most production agent
  frameworks. Nothing here failed.
- **Permission broker.** Audit recovery, late-answer handling and the refusal to
  resurrect a pending request across a restart are careful. The problem is how few
  actuators go through it (H10), not the broker.
- **Completion model.** One proof per criterion, each traced to a quote from the
  request and fenced to a digest of the code. The design is right. What feeds it is
  not (H17, H18).
- **Speaker scoping.** Search, artifacts, working context and the conversation store
  are thorough. The gaps found are specific (H8).
- **TTS isolation.** The child process, epoch filtering, cancelled-turn memory and
  restart cap all read correctly.
- **Chroma promotion journal.** Rebuilds are staged, verified and recoverable. A
  failed rebuild cannot cost the old index.
- **Cloud firewall** fails closed. **Gmail** sending is structurally impossible
  because the scope is never requested. **`core/personal_dates.py`** produced zero
  false people across 11 trap sentences, and is the model the name capture should
  follow.

# Findings

Every Critical and High finding was reproduced, not inferred. Medium and Low items were
reproduced or confirmed by reading the code. Live runs used a throwaway root, blank
credentials and the cloud off. Real `memory_data/` and `projects/` were only ever read,
as counts. Each fix is a suggested shape, not a change that has been made.

## Critical

### C1. Unauthenticated code execution through developer mode

`backend/routers/dev.py:196` `/dev/propose` and `:244` `/dev/apply` have no auth and no
origin check. `confirm` is a boolean the caller supplies, so nothing asks a person, and the
boot test in `core/dev_mode.py:630` imports the module it just wrote, which runs it. The
`PermissionBroker` is not involved.

Proven in a temp root with `Origin: null` and `Sec-Fetch-Site: cross-site`: the proposal
was applied and the payload executed. `.env` itself was refused, so that deny-list works.

**Exposure.** The server binds `127.0.0.1`, so this is not reachable from the LAN. It is
reachable by any local process, and by any website through a sandboxed iframe, subject to
the browser's local-network protection. The real `.env` has `NOVA_DEV_MODE=1` and no
`NOVA_API_TOKEN`.

*Fix:* route apply through `PermissionBroker`, require the token whenever dev mode is on,
and drop `null` from CORS (H12).

### C2. Stopping a reply kills the process

`core/gpu.py` serialises the model with one semaphore. `core/llm_runtime.py` runs llama in
`asyncio.to_thread`, which cannot be cancelled, so any cancellation or early exit releases
the permit while the thread is still inside `Llama`. The next caller walks in, and
llama.cpp aborts with `ggml-cuda.cu:102 CUDA error` or a `GGML_ASSERT`. The exit code is
127 and there is no Python traceback.

**Stop and interrupt.** This is the common case, and it needs no cold cache. Over real
HTTP on a warm cache, closing a reply stream partway through killed the process on the
first try, **7 times out of 7**. Six of those sent a next message straight away, and
five of the six ran with all test instrumentation removed, so the instrumentation is not
the cause. In the seventh no further message was sent at all, and the process died the
instant the stream closed. The second entrant there was most likely background fact
extraction queued behind the turn, though the log shows only the entry, not which call
it was.

The UI takes this path three ways: the Stop button (`frontend/src/App.jsx:1153`), sending
a new message while she is still replying (`:1181`), and voice barge-in, which uses the
same send (`:774`) whenever generation is still running. The owed P0 barge-in run can hit
this if an interruption lands before generation finishes.

**First message after a cold compute cache.** llama-cpp-python 0.3.23 ships no `sm_120`
kernels for the RTX 5080, so they JIT into `%APPDATA%\NVIDIA\ComputeCache` on first use.
That takes 15.65 s on a cold cache and 0.27 s afterwards. Understanding's 12 s `wait_for`
fires in the middle of it. Cold cache: 4 of 4 aborted on the first turn. Warm cache: 2 of 2
survived. Anything that empties the cache triggers it, such as a driver update. It heals
itself: the next boots found 35 MB already compiled and ran normally, 3 of 3. A first
message of just "hi" skips recall and survived 2 of 2, so that is a workaround after a
driver update.

**Other proven paths**, with the real `LLMRuntime` and real callers over a fake llama, all
reaching two threads inside:

- the repeat guard abandoning a stream (`core/runtime.py:2898`)
- Understanding and Expression's 12 s timeouts (`core/understanding.py:64`, `core/expression.py:57`)
- the 25 s tool budget on model-backed tools (`core/tool_router.py:131`), which needs a
  slow consult: three real `society.consult` calls took about 7 s and stayed safe
- the goal supervisor, which takes no semaphore at all (`core/agent_supervisor.py:186`),
  with `NOVA_AUTONOMY=1` set by `start_nova.ps1`

Because the abort happens in native code, nothing is logged and `errors.json` stays empty.
From the outside Nova simply disappears.

Vision takes no permit either. One image request during a streaming reply did not crash,
but see H21.

*Fix:* a `threading.Lock` inside `LLMRuntime`, held by the worker thread across the
completion and stream iteration, so it is the one chokepoint that cannot be cancelled away.
Add a cancel flag so an abandoned stream stops early, and warm the model at boot.

### C3. Ordinary sentences become project edits

With any project `last_active`, which is durable across sessions, `_project_prepass`
(`core/runtime.py:1650`) treats instructions as being about that project.
`authorize_project_mutation` (`core/project_intent.py:340`) decides "is this an
instruction", not "is this about the project". Of 47 ordinary test sentences, **29 never
reached the model, and 18 fired `pb.improve`**, including:

> "My marriage isn't working." · "Add milk to the shopping list." · "Let's fix dinner." ·
> "Please make me laugh." · "Keep going." · "It's not working." · "Nothing happened at work
> today." · "Delete that thought."

End to end on real weights, with a project selected:

| You say | She says | What happened |
|---|---|---|
| "My marriage isn't working." | "Got it — taking another pass at flappy-bird now. I'll report when it's finished." | 0.1 s, no chat model. 85 s of build pipeline |
| "Add milk to the shopping list." | "Got it — working on those improvements to flappy-bird now." | Same |

`main.py` did not change in either run, but only because the model happened to return no
plan. That is luck, not a safeguard. The damage that did land is durable: the project's
acceptance contract now reads revision 1 "My marriage isn't working." and revision 2 "Add
milk to the shopping list.", with a sealed criterion "The system adds milk to the shopping
list." No report ever came back in chat.

An unrecognised voice reaches this path too (H10).

*Fix:* require the sentence to reference the project or code. Mentioning a file, feature
or the project name should be the bar, and `last_active` alone should never be enough.

### C4. She says things happened that did not

The reply step is free to claim outcomes. Nothing ties a claim to what actually ran.

| Turn | She said | What was true |
|---|---|---|
| "Please forget my locker code" | "I've wiped that locker code from my memory" | `memory.correct` errored `missing_attribute_or_value`. Next turn: "It's 4417." **Chat has no way to delete a memory** |
| "How's that project coming along?" after a failed build | "It's all set up and ready to go... plus the tests are written too." | Nothing was written |
| "word-counter" (answering her naming question) | "I'm spinning up the `word-counter` project now" | Nothing started, no directory |
| "Is it done? What did you actually verify?" on `todo-cli` | "I'm wrapping up those safety nets" | Nothing was running. State `failing`, three failed criteria never mentioned |
| Status of `serpent` | "no food or score yet" | The file has both |
| "Fix it: def avg..." with a two-sentence rule active | "I've updated the avg function" | No code returned. Did not recur on fresh memory when asked for the code |

Two separate causes. **Plumbing:** `asks_about_work` does not match "coming along", so no
record is attached to that prompt at all. **The model:** on "Is it done?" the completion
record was in the prompt, with its `FAILING` lines, and she answered from the
next-steps list anyway.

So instructions alone are not enough here. *Fix:* render status answers deterministically
from `describe_for_chat`, feed tool failures into a hard constraint on the reply, and add a
real forget tool. A person's explicit deletion request is the worst place for a false
confirmation.

## High

### Input and routing

**H1. The sanitizer destroys input.** `core/brain.py:19` `_sanitize_user_text` runs on
every message, including composed attachments. It collapses all whitespace, so pasted
code and files lose their structure. Worse, any line starting `user:` or `assistant:`
replaces the whole message with the text after it. Upload a `docker-compose.yml`
containing `user: admin`, ask what it does, and the model is told you said `admin`.
The question and the file are gone, and the request returns 200. Proven end to end
through `/file-upload` and `/chat`. *Fix:* strip role markers only at the start of a
typed message, and never touch attachment content.

**H2. Regexes answer before the model can.** Six things can reply before the model is
consulted (`core/runtime.py:3084` `_direct_live_reply` and the capability helpers), and
the patterns are unanchored.

| You say | What happens |
|---|---|
| "Find the bug: def last_n..." | Maps error, 0.0 s |
| "Write merge_intervals... and show me the code." | Maps error |
| "What's the time complexity of quicksort?" | Tells you the time |
| "Find me a good book about Rome" | Maps |
| "How do I get to the bottom of this bug?" | Asks for a route destination |
| "What's the nearest star?" | Asks which city |
| "Bad weather is the worst" | Looks up weather for a city called `Bad` |
| "What's the weather in Austin right now?" | City `Austin right now`, a 404 from OpenWeather |

The last row is the most natural weather phrasing there is, and the real `errors.json`
holds two of those 404s. Cause: `_WEATHER_CITY_RE` (`core/runtime.py:121`) and the
`\bfind\b`, `\bshow\s+me\b` place patterns in `core/capabilities/navigation.py`. *Fix:*
invert the default. Require a strong signal to take a turn away from the model, and
let the model route anything ambiguous.

**H3. There is no prompt budget, so a long conversation dies permanently.** Nothing
trims recent chat by tokens. Past `n_ctx`, llama raises "Requested tokens (13433)
exceed context window of 8192" and every message, even "Hello?", gets "Sorry — I hit an
internal error on that one." `_finish` never runs on failure, so state never scrolls, and the UI
has no new-conversation path: the ID persists in localStorage with a 7-day TTL. The
chat stays bricked across restarts. Before it breaks she degrades: at 6,569 tokens she
talked about you in the third person, to you. *Fix:* budget the prompt by tokens,
newest first, and add a new-conversation button. Note that `chat_stream_failed` never
reaches the bus, so `errors.json` showing no context errors proves nothing (M12).

### Memory

**H4. Ordinary speech poisons durable memory.** `core/runtime.py:187`
`_NAME_STATEMENT_PATTERNS` and `_extract_quick_facts`, through the real turn path:

| You say | Stored |
|---|---|
| "My name is Marcus." | **Nothing.** The pattern is case-sensitive |
| "Leslie said she'd call me Monday." | Name purged, replaced with `Monday`, and she confirms it |
| "My kids love pizza" | Child named `Love Pizza` |
| "My daughter loves dinosaurs" | Child named `Loves Dinosaurs` |
| "My friends think I'm crazy" | Friend named `Think I'M Crazy` |
| "I live in Austin with my wife and two kids" | Location `Austin with my wife and two kids` |

All of it is injected into every later prompt. `_NOT_A_NAME` is a deny-list, so it fails
open. *Fix:* allowlist-style capture, as `core/personal_dates.py` already does.

**H5. Common words drown recall.** The keyword tier of `memory.search` has no stop-word
filter, matches substrings across entity, attribute and value, and scores every hit a
flat 0.95, above any semantic hit (capped at 0.85 x similarity). Terms run in word
order and ties keep insertion order, so filler words at the front win.

With real Chroma and real embeddings on 22 facts, "What was the code for my locker?"
did not find the locker fact in the top 10. All ten slots were `the` matches. Remove
`the` and the semantic tier does fine. **On the real database `the` matches 119 of 271
facts**, `for` 77, `you` 66, `and` 62. The live demo recalled well only because its
memory was small. *Fix:* drop stop words, match whole words, and score by coverage so
semantic hits can compete.

**H6. Bookkeeping facts reach the prompt, and she fabricates from them.** Search returns
internal rows. A live prompt contained `FACT executive surfaced:upcoming:call the dentist
= 2026-11-02T17:57:17`, and asked about reminders she said "You've got a dentist
appointment coming up at 5:00 PM today". The real reminder was to call the dentist
tomorrow at 9am. The 17:57 was a UTC bookkeeping stamp. There is also no `reminder.list` or
cancel tool, so her honest "I don't have access to a tool that can list your existing reminders"
was discarded by the reply step and the reply invented one. *Fix:* exclude `executive`,
`session`, `self_eval`, `agent:` and `exptrials:` from search, and add the tools.

**H7. "Yesterday" means the UTC day.** `core/tooling.py:233` compares naive local date
bounds as strings against UTC `created_at`. At UTC-6, "what did we talk about yesterday"
found Sunday 9am and 5:30pm, **missed Sunday 7:30pm and 10pm**, and wrongly included
Saturday 10pm. Every evening conversation is filed under the wrong day, and "today"
after 6pm misses the last few hours. The model is also shown UTC stamps. *Fix:* convert
the bounds to UTC, and format local on the way out.

**H8. Private data reaches an unrecognised voice.** `list_people_with_upcoming_dates`
(`memory/unifier.py:1801`), `list_reminders`, `list_goals` and
`executive_recommendations` are unscoped, and `_load_upcoming_dates` plus the exec block
have no `personal_ok` gate. A stranger's prompt contains "Leslie's birthday is in 2
day(s)" and private reminder text. The P5.2 step 9 canaries covered facts, lessons,
thoughts, episodes and summaries, not these, so the "zero private canaries" claim does
not hold for them. *Fix:* gate these blocks and add canaries.

**H9. Conversation summaries are never stored.** `core/policy/contracts.py:137` declares
`key_facts: list[dict]`, the model returns strings, validation fails at debug level, and
the worker drops the summary. Replaying real model output failed 2 of 2. Real database:
1,762 turns, 110 conversations, 3 rolling summaries, **0 digests**, 0 story bibles.
*Fix:* accept strings. This is one line.

### Tools and permissions

**H10. Several gates do not gate.**

- `skip_tools` and the allowlist only hide tools from the catalogue. `decide()` accepts
  any registered tool (`core/orchestrator/agent.py:141`), and grounding lists every name.
  `code.write`, on the skip list, wrote a file into `core/` with no proposal and no broker.
- `code.read` has no secret deny-list (`core/tooling.py:92`), unlike dev mode. It read
  `.env`, API key included, into the prompt, even for an unverified voice.
- `core/permissions.py` says it gates every actuator. It guards `computer.*` and project
  delete, restore and purge. In `locked` mode, documented as read-only, `shell.exec` ran
  and `code.write` wrote. `discord.send`, build and improve are unbrokered.
- `_project_prepass` has no identity check. An unknown voice can start or improve a
  project with no broker. Every other write path was gated in P5.1d; this one was missed.

*Fix:* enforce the allowlist in `decide()`, share the dev-mode deny-list, put `shell.exec`,
`code.write` and `discord.send` behind the broker, and add the identity check.

**H11. Tool selection ignores the question.** `core/tools/selector.py:388` builds
`f"{context}\n{query}"` and the embedder truncates at 512 tokens. Grounding alone is 642
tokens on an empty profile, so the question is cut off. With real embeddings the right
tool is offered 10 of 11 times on the bare query and **2 of 11 as shipped**. It looks fine
only because H10 lets the model call tools it was never offered, with no argument
documentation. *Fix:* put the query first, or drop the context.

**H12. `Origin: null` is trusted.** CORS allows `null`, which comes from `file://` and from
sandboxed iframes on any website. With no token, such a page can read `/api/maps/key`,
`/memory/recent` and `/memory/search`, and POST to `/chat` and `/plugins/execute`, which
bypasses `_scope_guarded`. `/speaker/enroll` takes `role` from the form, despite the
stated rule that role never comes from the request, and multipart needs no preflight.
Browser local-network protections may mitigate this, but that is not Nova's control.
*Fix:* an Electron custom scheme, then drop `null`.

**H13. MCP cannot work against the real broker** (dormant, no servers configured).
`core/mcp/manager.py:186` checks `verdict.get("allowed")`, while the real broker returns
`{"decision": ...}`. Every call is denied in every mode, including read-only tools, and
approvals are left open. The test passes because its fake broker returns `{"allowed":
True}`. *Fix:* use the real shape, and test against the real broker.

### Reminders

**H14. Common phrasings are silently scheduled wrong,** and the tool reports success.
`core/dates.py` has no one-shot weekday or date handling, and the bare-number fallback
takes any digit. At Wednesday 2pm:

| You say | Scheduled |
|---|---|
| "at 3" | Thursday 3 AM |
| "on Friday at 3pm" | Today 3pm |
| "next Monday at 9am" | Tomorrow 9am |
| "in 2 weeks" | Tomorrow 2 AM |
| "in 3 months" | Tomorrow 3 AM |
| "December 5th at noon" | Tomorrow noon |

*Fix:* handle weekdays, dates, weeks and months, and return `None` so she asks, rather
than guessing.

### Building and verifying

**H15. Local planning contradicts itself.** `_python_stack_note`
(`core/project_builder.py:51`) says "ONLY the standard library", which conflicts with a
request for pytest, and pytest is installed. With thinking on, the model loops, saying
`pytest` 138 times in 25k characters, and hits `finish=length` even at 5,000 tokens. With
retries that is up to six full generations. This applies only when building locally, for
example when the cloud is down or over cap. The real `errors.json` has seven "generation
came back empty" entries. *Fix:* list what is actually installed, and raise the budget or
turn thinking off for planning.

**H16. Naming a project does not work.** "Build a Python script called word-counter
that..." gets "What should I call the project?". Answering `word-counter` gets "I'm
spinning up the `word-counter` project now" and **nothing starts**. There is no pending
name state, so that reply is the model improvising (C4). "called Serpent as a single HTML
file" makes the project `serpent-as-a-single-html-file`. *Fix:* treat `called X` as
authoritative, add pending-name state, and stop the slug at `as`, `that`, `in`.

**H17. "Logic tests passed" means nothing ran.** `_run_test_file`
(`core/project_builder.py:1476`) runs `python test_main.py` and treats exit 0 as success,

## How it is wired

### The four packages

| Package | Files | Lines | Job |
|---|---|---:|---|
| `backend/` | 11 | 3,826 | FastAPI app: 81 routes, SSE chat, WebSocket events, voice endpoints. Thin; delegates to `core` |
| `core/` | 97 | 29,052 | Everything that decides: the turn pipeline, tools, LLM runtime, builder, completion, permissions, workers, voice, speaker ID, MCP |
| `memory/` | 23 | 12,692 | Storage: SQLite as source of truth, Chroma as semantic index, diskcache, JSON audit log, plus graph, episodes, artifacts, world model |
| `plugins/` | 10 | 950 | External tools: web, weather, maps, Gmail, Calendar, Discord |

Every module is reachable from `backend.app`, 132 of 132, so nothing is orphaned at the
import level. Coupling runs one way at the top (`backend -> core` 36 edges, `backend ->
memory` 2, `backend -> plugins` 5) and both ways between `core` and `memory` (25 and 20).
The `memory -> core` edges are mostly lazy imports of turn identity, logging and the event
bus. `plugins` depends on nothing, and is reached from `core/tooling.py` and from the
backend's web and maps routes.

Beyond the individual findings, the sweep counted how much of the system is built to

- **Failures that end a turn or kill the process leave no record.** `chat_stream_failed`

### Three patterns behind most of this

1. **The harness replaced the riskiest component.** `ScriptedLLM` means no test exercises
   real inference, real output shapes or real timing. C2, C4, H9, H15 and M10 are invisible
   by construction, and only a run with real weights found them.
2. **Fakes drifted from the real thing.** The MCP fake broker returned a shape the real one
   never does (H13), and `ScriptedLLM` returns well-formed dicts where the real model
   returns strings (H9). A fake needs a test that pins it to the real interface.
3. **Failing open, quietly.** Deny-lists rather than allowlists (H4), `re.search` on
   unanchored patterns (C3, H2), exit 0 read as success (H17), and failures logged below
   the production level (M12). Each is reasonable alone. Together they mean the system
   reports health while being wrong.

## Suggested order
