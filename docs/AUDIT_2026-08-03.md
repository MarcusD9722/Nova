## Findings and fixes

### 1. The event loop froze for up to 60s on every voice clip
`backend/app.py`'s `/stt` ran `ffmpeg` via `subprocess.run` **directly on the
event loop**. While a clip decoded, nothing else in Nova could progress: no
chat, no token streaming, no WS events, no workers. Found by AST sweep — no
test could see it, because the endpoint returns correct results either way.
Fixed onto a thread, along with the uploaded-audio write, `/file-upload`'s
unbounded `write_bytes`, and `shutil.rmtree` at shutdown.

### 2. One bad fact discarded an entire message's memory
`MemoryExtractorLLM` validated the fact batch as a unit, so a single attribute
outside the allowed set threw away every good fact beside it. *"My wife is
Leslie and my son is Mateo and my favourite colour is blue"* remembered
**nothing** — silently, at `debug` level. Facts are now validated individually;
partial extraction logs at INFO.

### 3. A memory that saved successfully and could never be read
`MemoryFact` accepts `attribute: "mom"|"dad"` because that is how people talk —
but grounding, `get_latest_fact` and the singleton-supersession set all read
`"mother"/"father"`. Such a fact was written, never found again, and never
superseded, so duplicates accumulated. Normalized at the contract boundary.

> Landmine for future work: the alias map **must** be module-level. As a
> leading-underscore *class* attribute, pydantic v2 turns it into a
> `ModelPrivateAttr` and every fact silently fails validation.

### 4. Contact PII reached the cloud provider
Found by the live test, not by inspection. The firewall drops structured
grounding blocks and redacts known names — but a task-shaped sentence kept its
contents, so Marcus's **street address was sent to OpenAI intact** while the
names around it were redacted.

Street addresses, emails and phone numbers are now redacted too. Deliberately
**redactions, not refusals**: refusing would silently disable cloud coding
whenever a prompt happened to contain an address, which is a worse failure than
sending `[address]`. Unlike name redaction, patterns don't depend on the
identity cache — which only a *chat turn* populates, so background
ProjectBuilder calls could previously reach the provider with it empty.

### 5. `upsert_text`'s own default argument crashed it
`ChromaMemoryBackend.upsert_text(metadata=None)` became `{}`, which chromadb
rejects outright. Latent — every current caller passes metadata — but the
signature advertised the broken call. Also now refuses a blank `doc_id` instead
of writing an unaddressable phantom row.

### 6. A degraded semantic index was invisible
`_chroma_upsert_safe` logged its warning **once, ever**, then swallowed
everything after. A broken index meant permanently degraded recall with one
buried log line and no further signal. Failures are now counted with the last
error retained and exposed as `semantic_index` on `/status`.

### 7. Every BOM'd file carried an invisible character into memory
`decode_text_bytes` tried `utf-8` before `utf-8-sig`, so plain utf-8 matched
first and left the byte-order mark in place. Every BOM'd file — the Windows
default for a lot of editors — carried a leading `﻿` into chat
attachments, indexed document chunks, and the embeddings built from them.
Reordered so `utf-8-sig` wins.

### 8. Nine of ten concurrent turns vanished from short-term memory
`ConversationStateStore.record_turn` is read-modify-write with no lock.
Measured: 10 concurrent calls kept **1**. Only one production path writes
today, but `/chat` and `/chat/stream` are separate endpoints, so a double-send
or an overlapping voice+text turn reaches it — and a lost turn disappears from
"Recent messages:" with no error anywhere. Added a write lock (writes are rare
and sub-millisecond, so contention is irrelevant).

### 9. `/memory/purge` failed OPEN on the destructive path
The admin guard returned silently when `NOVA_ADMIN_TOKEN` was unset — and it
is unset here, as is `NOVA_API_TOKEN`. An unauthenticated `POST /memory/purge`
with `dry_run:false` deleted facts and answered `200`.

Scope, stated precisely: `dry_run` **defaults to true**, so this was never
"one stray POST wipes everything" — it took a deliberate `dry_run:false`. Real
nonetheless. Now fails closed with a message naming what to configure; dry runs
stay open so the data remains inspectable. Nothing called it (not the UI, and
`runtime.py` uses `purge_facts` directly), so failing closed breaks nothing.

### 10. A broken memory capture would have been silent forever
The four capture pre-passes on every chat turn (`_extract_quick_facts`,
`_capture_lessons`, `_capture_mood`, `_capture_wellbeing`) each sat in a bare
`except: pass`, as did the memory-ingest enqueue. A capture that started
raising would stop recording facts, lessons and mood **permanently**, with no
signal. Not hypothetical: a `BUS.publish` NameError in `_capture_mood` survived
an entire development round because these blocks hid it. Control flow is
unchanged (capture must never break a turn); the failure is now logged with
the stage name and the real error.

### 11. The error handler killed the worker it was reporting for ⚠️ worst one
`MemoryIngestWorker._run` caught an ingest exception and called
`logger.exception(...)`. structlog's console renderer draws its traceback with
box characters (`│ ┌ ─ →`); on a Windows **cp1252** console `print()` raises
`UnicodeEncodeError` — **from inside the except block**. That propagated out of
`_run` and killed the task.

Consequence: one ordinary ingest error (a bad LLM response, a transient DB
hiccup) **permanently stopped every long-term memory write for the rest of the
session**. Chat kept working perfectly, so there was nothing to notice.

Found because the test's own worker died mid-suite. Two fixes:
- **Cause:** `logging_setup` now forces UTF-8 with `errors="replace"` on stdout
  and stderr. A mangled character in a log line beats losing a worker.
- **Belt:** `log_worker_error()` in `core/workers/lifecycle.py` — any logging
  failure at all degrades to a plain stderr line instead of propagating.

### 12. Queued turns were discarded at shutdown
`MemoryIngestWorker._run` exits at the top of the loop once `_stop` is set, so
anything still queued was thrown away. Those are the most recent things said,
and the turn itself had already succeeded, so the loss was invisible.
`stop()` now drains the backlog (10s budget) before signalling stop, and says
so if the drain doesn't complete.

### 13. A crashing plan orphaned its task forever
`AutonomySupervisorWorker` claims a task (marking it *running*) before planning.
Anything raising between claim and `mark_task_done` left it running
permanently — never finished, never retried, invisible until the next boot
cleared stale work. `agent_supervisor` already had this fix; the autonomy one
did not. It now releases the claim as `failed` with the real error.

### 14. ~590 lines of dead policy code, built fresh on every boot
`RuntimeManager.__init__` constructed `ChatDecider` and `ResponseComposer` and
then never used either — P4 unified `/chat` and `/chat/stream` onto one pipeline
and stopped calling them, but the assignments stayed. `ChatDecider` also held
the *only* reference to `FollowUpGeneratorLLM`.

Removed both instantiations (`runtime.py` 1,884 → 1,877). That leaves
`chat_decider.py`, `followup_generator.py` and `response_composer.py` —
~590 lines — completely unreachable. Left on disk rather than deleted
unilaterally, since deep-mode composition is a plausible future caller; they
are tested and harmless where they sit. **Delete them whenever you're sure.**

### 15. A failing tool was recorded as a success, and never retried
`AgentSupervisor` wrapped `self._router.execute(...)` in a try/except and put
its whole retry-with-backoff branch in the `except`. But **`ToolRouter.execute`
never raises** — it catches everything and returns `ToolResult(ok=False)`.

So the entire retry branch was dead code: `max_retries` never applied,
`bump_goal_task_attempt` was never called, and a tool that failed was completed
with status **`"done"`**. The goal's own history then read `DONE <tool>`, so the
next `__decide__` step was told the step had succeeded and planned on top of a
failure. Failure is signalled by `ok`, so that is what is checked now.

### 16. The same two worker bugs, again, in agent_supervisor
Both patterns from findings 11 and 13 were present here too and are now fixed:
`logger.exception` in the loop handler (which did raise `UnicodeEncodeError`
and kill the supervisor during the test run), and a claimed task orphaned
forever when a decision was malformed — an unknown `type`, or a `tool`
decision with a blank name.

### 17 & 18. (From the U10 phase, same session)
Worker `stop()` let `CancelledError` escape, aborting shutdown halfway; and
cancelling mid-transaction leaked aiosqlite's non-daemon thread so the process
never exited (~1 run in 6). Both fixed in `core/workers/lifecycle.py`.

## Verified working — no changes needed

- `core/code_ops.py` is already correctly async (aiofiles + `to_thread` for the
  atomic replace).
- `extract_first_json_object` survived every adversarial input thrown at it:
  prose-wrapped, fenced, nested, braces inside strings, escaped quotes, two
  objects, 200KB payloads. Documented limits: single-quoted pseudo-JSON and
  trailing commas are rejected.
- `AutonomyPlannerLLM` correctly strips hallucinated tools not in the registry.
- Every policy class properly serializes on the GPU semaphore.
- `WorldModel` enforces its provenance rule: unsourced triples are refused.
- `web.search` drops DDG ad/tracker redirects and raises on HTTP errors rather
  than returning "no results" (which would read as "the web had nothing").

## Deliberately NOT changed

**11 sync `mkdir` calls and ~16 small `read_text`/`write_text` calls inside
async functions.** These are microsecond-to-sub-millisecond syscalls on local
files. Wrapping them in `asyncio.to_thread` costs more in thread-pool overhead
than the call itself, and during a project build the LLM call beside them takes
*seconds*. Converting them would be cargo-cult async. The ones that mattered —
unbounded or subprocess-backed — are fixed.

**Most of the 92 `except: pass` sites.** All were reviewed by listing the
statement each one guards. The overwhelming majority are genuinely best-effort
enrichment — grounding-context loaders, `Expression` phrasing, Chroma id
deletes — where failing to "no enrichment" is the correct behavior and logging
would be noise on every turn. The five that sat on the per-turn memory-capture
path were fixed (finding 10); the rest are left deliberately.

## Pattern worth remembering

Three separate modules had the **same two bugs**, and each was found only by a
test that made a worker actually fail:

1. `logger.exception(...)` inside a worker's own except handler, which can
   raise and kill the worker (`memory_ingest`, `agent_supervisor`).
2. A task claimed (marked *running*) before work begins, then orphaned forever
   when anything in between raised (`autonomy_supervisor`, `agent_supervisor`;
   `agent_supervisor` had a partial guard covering only one of three paths).

Any future worker should use `log_worker_error()` and release its claim in the
except handler. Worth checking new ones against both.

## Next

Everything in the four packages now has coverage. Remaining ideas, in order of
value:

- **Test the failure paths that only appear under load** — the integration
  harness can drive concurrent turns, but nothing yet simulates a slow disk,
  a full queue, or SQLite lock contention.
- Three things worth considering separately:

- **Delete the ~590 lines of unreachable policy code** (finding 14) once you're
  sure deep mode won't want them.

- **`web.fetch` has no SSRF guard.** It will fetch `http://127.0.0.1:8008/...`
  or a cloud metadata address if the agent is handed such a URL. With
  `NOVA_API_TOKEN` unset, Nova's own endpoints are reachable that way. Not
  exploited by anything today (URLs come from Marcus or from search results),
  so it is noted rather than changed — a private-IP blocklist is the fix.
- **`NOVA_ADMIN_TOKEN` and `NOVA_API_TOKEN` are both unset.** Fine for
  localhost-only use, which is the current posture, and the boot log already
  warns. Worth setting before any 24/7 or multi-device exposure.
