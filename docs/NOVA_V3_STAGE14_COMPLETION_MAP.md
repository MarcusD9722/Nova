## The one decision that produces "complete"

Two places, character-identical, at
[`project_builder.py:868`](../core/project_builder.py) (fresh build) and
[`project_builder.py:1336`](../core/project_builder.py) (improvement):

```python
run_ok = run_note is None or run_note.startswith("Run check passed")
tests_inconclusive = bool(test_note and test_note.startswith("Logic tests inconclusive"))
status = "needs attention" if not run_ok else ("needs review" if tests_inconclusive else "complete")
```

That is the whole of it. Everything Nova durably calls "complete" comes from
those three lines, and they consult exactly two things:

| input | what it actually proves | when it is `None` |
|---|---|---|
| `run_note` | the entry point started and did not crash within the timeout | run check disabled; **no runnable `.py` entry at all** (a pure-HTML project, or only test files) |
| `test_note` | tests *Nova generated by reading her own output* did not object | logic tests disabled; nothing importable |

**The user's request appears nowhere in this decision.** There is no
representation of what was asked for, so there is nothing to compare the
result against.

Note also which `test_note` values are *not* treated as a problem:

- `"No automated logic tests were applicable."`
- `"No reliable logic tests could be generated."`

Both mean *nothing was verified*, and both fall through to `complete`. Only the
literal prefix `"Logic tests inconclusive"` softens the verdict.

### A path that looks like a defect and is not

`_verify_and_fix_runtime` ends with `return None` at line 957, which would make
`run_ok` true after a failed run. It is unreachable: every branch on
`attempt == 2` returns first. Recorded so the next reader does not re-file it.

## Layers that carry completion-like state

| layer | who writes | durable? | what evidence caused it | survives restart |
|---|---|---|---|---|
| `PROJECT.md` `## Status` | `_write_project_md` | yes, file | the three lines above | yes |
| `PROJECT.md` progress log | same | yes, file | build_log list | yes |
| memory fact `project:<slug>/status` | `_save_fact` | yes, SQLite | same | yes |
| `project.completed` event | `BUS.publish` | no, in-memory bus | same | no |
| episodic episode | `episodic_promoter._note_project` | yes | carries `status` into `outcome` | yes |
| frontend chat line | `useNovaBusEffects.js` | no | branches on `d.status` | no |
| goal/task rows | Stage 13B/13C machinery | yes | **unrelated to project completion** | yes |

### Consumers of `project.completed`

- `core/episodic_promoter.py:394` — records `"Nova finished <slug> (<status>)"`, carrying status through. **Honest.**
- `frontend/src/hooks/useNovaBusEffects.js:42` — branches on `d.status` for `needs attention` / `needs review` / improve / else. **Honest.**
- `frontend/src/hooks/useNovaEvents.js:78` — flashes an indicator on `completed || error`, keyed on **type alone**. Cosmetic, but it is a consumer that cannot tell the two apart.
- `frontend/src/App.jsx:1906` — refreshes project views on type.

So the current in-repo consumers mostly read `status`. The defect is that the
*event contract* permits them not to, and the name asserts something the
payload then retracts.

## Reproductions on the untouched base

All three drive the real `ProjectBuilder`, not a simulation.

### S14-1 — partial improvement reports COMPLETE

Requested A + B + C. `a.py` generated fine; `b.py` came back empty and was
**skipped**; `c.py` had a syntax error and was **compile-reverted**.

```
b.py implemented: False
c.py implemented: False
PROJECT.md ## Status      -> complete
memory fact status        -> 'complete'
project.completed         -> status='complete' files=['a.py']
                             summary='add features A, B and C'
progress log              -> "Improved: a.py - add features A, B and C"
```

`fail_reasons` is collected at lines 1304 and 1320 and read **only** at line
1324, inside `if not changed:`. So the failures surface when *everything*
fails, and are discarded the moment one file succeeds — exactly the case where
a person is most likely to be misled.

### S14-2 — a calculator that cannot subtract is COMPLETE

Brief: *"a calculator that can add and subtract two numbers"*. Generated code
implements `add` only, starts cleanly, and produces no applicable tests.

```
can add:      True
can subtract: False

## Brief    a calculator that can add and subtract two numbers
## Status   complete
## Summary  a calculator with add and subtract
log         Wrote 1 file(s). Build complete.
            Run check passed (main.py).
            No automated logic tests were applicable.
```

The requirement is four lines above the verdict in the same file, and nothing
compares them. "No automated logic tests were applicable" — *nothing was
verified* — reaches the same verdict as passing would.

### S14-3 — "Build complete." on a project that needs attention

Generated program crashes on every run; the repair loop exhausts.

```
## Status   needs attention
log         Wrote 1 file(s). Build complete.        <- two lines above
            Run check still failing after fixes: Traceback...
project.completed published, status='needs attention'
```

`build_log[0]` is written before any validation has happened and is never
revisited, so one file contradicts itself; and an event named `completed` is
published for a build that did not.

## What this map says the stage must build

1. A durable representation of **what was asked for** — acceptance criteria —
   because no amount of tidying the three lines above can compare a result to a
   request that was never recorded.
2. Evidence that names the criterion it proves, fenced to the requirement
   revision and the artifact it actually examined.
3. One deterministic evaluator, so no writer can assign the string `complete`.
4. Event and projection names that mean what they say.

The circularity is worth stating plainly, because it is attack target 5 and it
is real: today the only behavioural evidence Nova has is a test she generated
by reading the code she just wrote. That tests self-consistency. It cannot
test whether the code does what the user asked, because the user's request was
never part of the comparison.
